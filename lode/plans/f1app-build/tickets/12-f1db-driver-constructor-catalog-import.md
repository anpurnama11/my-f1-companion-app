# 12 — F1DB driver + constructor catalog import (build-time)

**What to build:** the F1DB build-time import that powers the
redesigned DriverDetail / TeamDetail screens (wayfinder ticket 26 +
ADR 0012). Three Kotlin `object` catalogs at
`app/src/main/java/com/anpurnama/f1_app/f1/data/`, generated by a new
sister Python script that downloads the pinned F1DB JSON + YAML and
emits Kotlin source. The catalog is build-time data only — never
parsed at runtime, never fetched over the network at runtime (same
precedent as the existing `tools/f1db/import-circuit-artwork.py`).

**Concretely:**

- New sister script: `tools/f1db/import-driver-constructor-catalog.py`
  (alongside `tools/f1db/import-circuit-artwork.py`; not an extension
  of it — different concerns, different deps).
- New F1DB revision pin: `tools/f1db/catalog-revision.txt` at
  `v2026.10.1` (the research revision; separate from the artwork
  pin at `v2026.0.1`).
- New generated file:
  `app/src/main/java/com/anpurnama/f1_app/f1/data/DriverCatalog.kt`
  — `object` with `forId(driverId): DriverStats?`.
- New generated file:
  `app/src/main/java/com/anpurnama/f1_app/f1/data/ConstructorCatalog.kt`
  — `object` with `forId(constructorId): ConstructorStats?`.
- New generated file:
  `app/src/main/java/com/anpurnama/f1_app/f1/data/TeamSeasonalFacts.kt`
  — `object` with `forId(constructorId): TeamFactsRow?` (3 fields
  only: chassis, power unit, base country; current season).
- Each generated file's KDoc carries the F1DB CC BY 4.0 attribution.
- `Wiring` exposes the three catalogs as `val` properties (object
  references, no instantiation).
- Three JVM unit tests at
  `app/src/test/java/com/anpurnama/f1_app/f1/data/`: `DriverCatalogTest`,
  `ConstructorCatalogTest`, `TeamSeasonalFactsTest`. Mirror the
  existing `CircuitArtworkTest` shape.
- Extend `THIRD_PARTY_NOTICES.md` F1DB section to include the three
  catalog files + the catalog revision pin.

## Acceptance summary — the hard gate

The script prints this summary at the end and uses it as the exit gate:

```
Antonelli 2026: 6W / 8P / 6 poles / 1 DNF / 183 race points
Mercedes 2026: F1 W17 (chassis) / Mercedes (power unit) / Germany (base country)
```

If both lines match, the script writes the three Kotlin files and
exits 0. If either mismatches, the script writes nothing and exits
non-zero. A partial file is never left in the working tree.

The values come from the api-wrangling doc's live probes
([`driver-team-detail-api-wrangling.md`](../../../wayfinder/f1app/driver-team-detail-api-wrangling.md)):

- Antonelli 2026 wins = count of `positionText == "1"` in
  `races-race-results.json` for `(kimi-antonelli, 2026)` = 6.
- Antonelli 2026 podiums = count of `positionNumber in 1..3` = 8.
- Antonelli 2026 poles = count of `gridPositionText == "1"` = 6.
- Antonelli 2026 DNFs = count of `reasonRetired != null AND
  positionNumber == null` = 1 (R7 Collision; R9 Spin is classified
  at position 14, NOT a DNF).
- Antonelli 2026 race points = sum of `points` for
  `(kimi-antonelli, 2026)` in `races-race-results.json` = 183
  (sprint points excluded — they live in
  `races-sprint-race-results.json`, which this script does not read).
  The 21-point delta to the 204 championship total is sprint-only.
- Mercedes 2026 chassis = `chassis.yml` `name` field for
  `mercedes-f1-w17` = `"F1 W17"`.
- Mercedes 2026 power unit = `engine-manufacturers.yml` `name`
  field for `mercedes` = `"Mercedes"`.
- Mercedes 2026 base country = `countryId` from
  `seasons/2026/entrants.yml` for Mercedes = `germany` (lowercase
  F1DB id; the screen renders the user-facing country name from a
  small static map; the catalog stores the F1DB id and the screen
  resolves it).

## Aggregation rules (locked per ticket 26 + api-wrangling doc)

- **DNF**: `reasonRetired != null AND positionNumber == null`.
  Excludes classified retirements (R9 Antonelli 2026 "Spin" —
  positionNumber 14, classified). Excludes DSQ with a classified
  position. Hits the "1 DNF in 2026" acceptance.
- **Top10**: `positionNumber != null AND positionNumber <= 10`.
  Excludes unclassified rows.
- **Pole**: `gridPositionText == "1"` (per-row grid). The
  `polePosition` boolean is a race-level flag, not the per-row
  indicator; the script uses the per-row field.
- **Win**: `positionText == "1"`.
- **Podium**: `positionNumber in 1..3`.
- **Race-only filter**: use
  `f1db-races-race-results.json` (the main race results file). The
  `total*` fields on `f1db-drivers.json` / `f1db-constructors.json`
  include sprint rounds; the script does not use them for all-time
  counts. Sprint data lives in a separate
  `f1db-races-sprint-race-results.json` file; the script does not
  read it.
- **First entry**: first row of `f1db-races-race-results.json` for
  the driver (or constructor), sorted by `(year, round)`. The
  display name is the joined `name` field from
  `f1db-grands-prix.json` (joined via `raceId`). The catalog stores
  the `raceId`; the screen resolves the name from a small static
  `grands-prix-name.json` companion file (or the script can inline
  the join; the build ticket locks the choice: **inline the join** —
  the generated catalog stores the display name directly so the
  runtime never touches `f1db-grands-prix.json`).
- **First win**: first row with `positionText == "1"`, same sort +
  same inline name join.
- **World Championships**: `totalChampionshipWins` field on the
  driver/constructor row in `f1db-drivers.json` /
  `f1db-constructors.json`. Cross-check (script-side, not at
  runtime): count of `positionNumber == 1` rows in
  `f1db-seasons-{drivers,constructors}.json` should match. Mismatch
  is a script bug, not a runtime bug.
- **Per-season aggregates**: take the row from
  `f1db-seasons-{drivers,constructors}.json` for
  `(driverId/constructorId, year)`. DNFs and top10s are NOT in this
  file — the script must aggregate them from
  `f1db-races-race-results.json` filtered to the same
  `(driverId, year)` (or `(constructorId, year)`).

## F1DB data sources

The script reads from F1DB **v2026.10.1** (pinned in
`tools/f1db/catalog-revision.txt`):

```text
JSON (from f1db-json-splitted.zip in the v2026.10.1 release):
  f1db-drivers.json               # career totals, first/last season
  f1db-constructors.json          # career totals
  f1db-seasons-drivers.json       # per-season aggregates
  f1db-seasons-constructors.json  # per-season aggregates
  f1db-races-race-results.json    # per-round race results (race-only)
  f1db-grands-prix.json           # race name lookup by id

YAML (from raw.githubusercontent.com, pinned to the same revision):
  src/data/seasons/{year}/entrants.yml          # chassisId / engineManufacturerId / countryId per team
  src/data/chassis/{chassisId}.yml              # name field (e.g. "F1 W17")
  src/data/engine-manufacturers/{id}.yml        # name field (e.g. "Mercedes")
```

For 2026, the YAML fan-out is 1 entrants file + 11 chassis files + 5
engine-manufacturer files = 17 HTTP requests. The script caches them
in a local temp dir for re-runs; re-runs within a single script
invocation reuse the same temp dir.

For **future seasons** the script rerun generates a fresh
`TeamSeasonalFacts.kt` from the new `seasons/{year}/entrants.yml` —
no code change at season launch, just rerun the import with the new
year as a CLI argument (default: current year).

## Generated Kotlin shape (full)

```kotlin
// app/src/main/java/com/anpurnama/f1_app/f1/data/DriverCatalog.kt
package com.anpurnama.f1_app.f1.data

/**
 * F1DB driver statistics catalog. Generated by
 * `tools/f1db/import-driver-constructor-catalog.py` from F1DB
 * v{revision}. F1DB is licensed under CC BY 4.0
 * (<https://creativecommons.org/licenses/by/4.0/>); attribution is
 * retained here per the license terms.
 *
 * @see <https://github.com/f1db/f1db>
 */
object DriverCatalog {
    private val byId: Map<String, DriverStats> = mapOf(
        "kimi-antonelli" to DriverStats(/* ... */),
        // ... every F1 driver, sorted alphabetically by F1DB id
    )

    fun forId(driverId: String): DriverStats? = byId[driverId]
}

data class DriverStats(
    val allTime: DriverAllTimeStats,
    val bySeason: Map<Int, SeasonDriverStats>,
)

data class DriverAllTimeStats(
    val raceEntries: Int,         // race-only count (sprint filtered)
    val raceWins: Int,            // race-only
    val podiums: Int,             // race-only
    val polePositions: Int,       // race-only
    val points: Double,           // race-only
    val fastestLaps: Int,         // race-only
    val top10s: Int,              // race-only
    val dnfs: Int,                // race-only
    val championshipWins: Int,
    val firstEntryRaceName: String?,
    val firstWinRaceName: String?,
    val firstSeasonYear: Int,
    val lastSeasonYear: Int,
)

data class SeasonDriverStats(
    val position: Int?,           // null if mid-season
    val wins: Int,                // from f1db-seasons-drivers.json (race-only)
    val podiums: Int,             // from f1db-seasons-drivers.json (race-only)
    val poles: Int,               // from f1db-seasons-drivers.json (race-only)
    val points: Double,           // from f1db-seasons-drivers.json (race-only)
    val fastestLaps: Int,         // from f1db-seasons-drivers.json (race-only)
    val top10s: Int,              // aggregated from races-race-results.json (race-only)
    val dnfs: Int,                // aggregated from races-race-results.json (race-only)
)
```

```kotlin
// app/src/main/java/com/anpurnama/f1_app/f1/data/TeamSeasonalFacts.kt
package com.anpurnama.f1_app.f1.data

/**
 * F1DB YAML-sourced per-season team facts (chassis, power unit,
 * base country). Generated by
 * `tools/f1db/import-driver-constructor-catalog.py` from F1DB
 * v{revision}. F1DB is licensed under CC BY 4.0.
 *
 * Source: `seasons/{year}/entrants.yml` resolved via
 * `chassis.yml` (chassis name) and `engine-manufacturers.yml`
 * (manufacturer name). 3 fields only — base city and team
 * principal were dropped from the new screen per wayfinder
 * ticket 26.
 *
 * @see <https://github.com/f1db/f1db>
 */
object TeamSeasonalFacts {
    private val byId: Map<String, TeamFactsRow> = mapOf(
        "mercedes" to TeamFactsRow(
            season = 2026,
            chassis = "F1 W17",
            powerUnit = "Mercedes",
            baseCountryId = "germany",
        ),
        // ... every 2026 constructor, sorted alphabetically by F1DB id
    )

    fun forId(constructorId: String): TeamFactsRow? = byId[constructorId]
}

data class TeamFactsRow(
    val season: Int,
    val chassis: String,         // e.g. "F1 W17"
    val powerUnit: String,       // e.g. "Mercedes"
    val baseCountryId: String,   // F1DB country id, e.g. "germany"
                                  // (the screen renders the user-facing
                                  // name via a small static map)
)
```

`baseCountryId` is stored as the F1DB id (e.g. `"germany"`,
`"united-kingdom"`, `"italy"`) because F1DB is the source of truth
for the id and a small static map at the screen layer resolves the
user-facing name. The catalog does not duplicate the user-facing
name; one source of truth (F1DB id), one resolver (the screen).

## Invariants

- The three generated catalog files are deterministic from the pinned
  F1DB revision: same input → same output bytes. The script sorts
  every map by F1DB id before emitting; Python's `json.dumps` uses
  `sort_keys=True`; the Kotlin literal uses a `mapOf(...)` with
  sorted-key insertion order.
- The script writes the Kotlin files only after the acceptance
  summary matches; a failed acceptance exits non-zero and writes
  nothing (no partial file in the working tree).
- The script reads `f1db-races-race-results.json` (race-only) and
  NEVER reads `f1db-races-sprint-race-results.json`. Sprint data
  does not enter the catalog.
- The catalogs are keyed by f1api.dev `driverId` / `teamId` (the
  same keys used in the rest of the app), NOT by F1DB's internal
  ids. The script joins F1DB ids to f1api.dev ids by matching
  `firstName` + `lastName` (for drivers) and `name` (for
  constructors). The mapping is deterministic; the script logs any
  unmapped ids to stderr and treats them as fatal (the catalog
  must cover every current f1api.dev driver/team, otherwise the
  new detail screen has gaps).
- `Wiring` exposes the catalogs as object references (singletons);
  no factory methods, no DI graph complexity.
- The script pins to `v2026.10.1` via `catalog-revision.txt` and
  never reads the latest release — the user approves a version
  bump explicitly.
